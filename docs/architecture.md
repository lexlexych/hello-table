### Независимый OpenAI Realtime-режим по ресторану (19.08.2026)

`restaurants.voice_mode` хранит один из двух вариантов: `pipeline` (безопасное значение по
умолчанию) или `realtime`. Агент читает его точечной `SECURITY DEFINER`-функцией
`get_agent_runtime_settings(uuid)` под ролью `agent_app` до сборки сессии. Выбор фиксируется
на весь звонок: изменение администратором влияет только на следующую сессию и не пытается
заменить аудиограф уже идущего разговора.

`realtime` — отдельная ветка, а не ускоритель существующего конвейера. В ней создаётся только
`openai.realtime.RealtimeModel` (`gpt-realtime-2.1`, `reasoning.effort=minimal`, semantic VAD,
настраиваемый голос). Отдельные `openai.STT`, `openai.LLM`, `OpenAIStreamingTTS` и Silero VAD
не создаются. `inputAudioTranscription` также задан как `null`: даже вспомогательная
`gpt-4o-mini-transcribe` из умолчаний плагина была бы отдельным STT и для понимания аудио
Realtime-моделью не нужна. Поэтому Realtime непосредственно понимает входное аудио, выбирает
язык ответа по речи и возвращает аудио, а портал в этом режиме не получает расшифровку гостя.

Обе ветки используют одного `RestaurantAgent` и одинаковые Postgres-инструменты. Ни одна
ветка не добавляет речь до или после RPC: инструменты только выполняют запрос и возвращают
структурированный результат. Pipeline берёт язык ошибок из `LanguageTracker`, а Realtime
передаёт `language: de|ru|en` в аргументах инструмента. Это нужно для локализации меню,
ошибок и языка брони, потому что audio-to-audio событие не даёт приложению надёжный код
языка для синхронного переключения состояния. Русский локальный `fillerN.wav` относится к
пользовательскому ходу Pipeline и запускается до генерации ответа независимо от tool calling.

Юридическое объявление остаётся первой фразой. В Realtime вход участника временно выключен,
после старта сессии вызывается `generateReply` со строгой инструкцией произнести объявление
и приветствие, после окончания проигрывания вход включается. В отличие от pipeline это
генерация моделью, поэтому буквальное совпадение текста не гарантируется и проверяется
вручную на DE/RU/EN. Автоматического fallback на pipeline нет: иначе сохранённая настройка,
стоимость и диагностика расходились бы с реальностью.

Официальная Realtime API поддерживает EU regional processing для выбранной модели через
EU-проект и `https://eu.api.openai.com/v1`; tracing не включается, поскольку для него такая
гарантия не заявлена. Перед боевым использованием всё равно обязательны DPA/ZDR и живое
подтверждение проекта. Ожидаемое снижение задержки относительно STT→LLM→TTS считается
гипотезой до парного ручного замера; стоимость сравнивается по usage фактических звонков.

## Результаты обязательных проверок

### Переход STT и TTS с ElevenLabs на OpenAI (18.08.2026)

По решению владельца тестовая голосовая цепочка переведена на `gpt-transcribe` и `tts-1`.
Обе модели подключены существующим `@livekit/agents-plugin-openai` 1.6.4; отдельный SDK и
второй API-ключ больше не нужны. Плагин ElevenLabs и его локальный patch удалены.

`gpt-transcribe` выбран вместо `gpt-realtime-whisper`, потому что финальное событие модели
содержит определённые языки. Это сохраняет текущий контракт `LanguageTracker`, выбор
фиксированных i18n-фраз и запись `reservations.language`. `AGENT_ENABLED_LANGUAGES`
передаётся как список language hints, `detectLanguage: false` не запрещает модели вернуть
фактический язык, а только не даёт плагину удалить эти hints из конфигурации. Реплику
коммитит server VAD OpenAI с порогом `STT_VAD_SILENCE_THRESHOLD_MS`.

`tts-1` выбран как модель OpenAI, оптимизированная под минимальную задержку. Общий голос
задаётся `TTS_VOICE`, переопределения DE/RU/EN сохранены. Сам Speech API поддерживает
chunked streaming, но Node-плагин 1.6.4 объявляет `streaming: false` и читает весь
`arrayBuffer()` до выдачи аудиофреймов. Первый ручной замер на трёх репликах подтвердил
узкое место: `ttsTtfb` p50 2031 мс, max 2267 мс при общей p50 5128 мс.

Поэтому поверх Speech API добавлен локальный `OpenAIStreamingTTS`: он запрашивает сырой
24 kHz mono PCM, читает `Response.body` без промежуточного `arrayBuffer()` и сразу отдаёт
LiveKit 20-мс фреймы. Возможность `streaming` у LiveKit оставлена `false`, потому что она
описывает потоковый **ввод текста**, которого у Speech API нет. Фреймворк продолжает
делить токены LLM на законченные предложения, а адаптер потоково выдаёт аудио каждого
предложения. Это сохраняет просодию на границах предложений и сокращает TTFB без дробления
текста на искусственные короткие фразы. Отмена LiveKit прерывает тот же HTTP-запрос, поэтому
при перебивании остаток ответа не буферизуется.

Один `OPENAI_BASE_URL` применяется к STT, LLM и TTS. Официальная региональная матрица
подтверждает EU processing для `tts-1`, но не перечисляет `gpt-transcribe` для Realtime
transcription sessions. До подтверждения живым запросом из EU-проекта эта конфигурация
разрешена только для синтетических тестов без персональных данных.

По явному указанию владельца автоматические проверки TTS не создаются и не запускаются;
пригодность цепочки и новый TTFB он оценивает самостоятельным звонком по
`docs/manual-tests.md` §4.

### Стриминг Voxtral Realtime в `@livekit/agents-plugin-mistralai` (итерация 3, PROJECT.md §2.3)

⚠️ **Раздел исторический: с 18.08.2026 распознавание переведено на ElevenLabs Scribe**
(следующий раздел). Разбор сохранён — он объясняет, откуда взялись требования к Silero VAD
и почему определение языка не пишется своими силами.

**Статус: проверено 15.08.2026. Ответ — стриминг ЕСТЬ. Работаем как задумано,
кастомный STT-плагин и Deepgram не нужны.**

Что проверялось: `@livekit/agents-plugin-mistralai` **1.6.4** (опубликована 14.08.2026,
последняя стабильная), `@livekit/agents` 1.6.4, транзитивно `@mistralai/mistralai` 2.6.3.
Метод — статический разбор исходников пакета (пакет публикует `src/`, не только `dist/`).
Живой звонок с реальным ключом не выполнялся: реальные ключи и вызовы внешних API
запрещены в автоматической проверке (AGENTS.md §4), это шаг ручного теста.

**Доказательства:**

1. `STT` объявляет возможности динамически, по имени модели:
   `super({ streaming: isRealtime(model), interimResults: isRealtime(model) })`,
   где `isRealtime` = имя модели содержит `realtime`. Для
   `voxtral-mini-transcribe-realtime-2602` (модель из PROJECT.md §2 — присутствует
   в union `MistralSTTModels`, имя верное) это даёт `streaming: true`.
2. `STT.stream()` возвращает `SpeechStream`, работающий через
   `RealtimeTranscription` из `@mistralai/mistralai/extra/realtime`. Это настоящий
   WebSocket: модуль импортирует `ws`, соединение живёт как `RealtimeConnection`
   с `sendAudio()` / `flushAudio()` / `endAudio()` и асинхронным итератором событий.
   Для нереалтаймовой модели `stream()` бросает исключение с внятным текстом.
3. Промежуточные результаты приходят: событие `transcription.text.delta` →
   `INTERIM_TRANSCRIPT`, событие `transcription.done` → `FINAL_TRANSCRIPT`.
   Аудио отправляется чанками по 50 мс, 16 кГц моно PCM16.
4. **Язык определяется сервером и сообщается клиенту** — событие
   `transcription.language` c полем `audioLanguage`. Это ровно то, на чём построен
   §4.1 (фиксация языка сессии по первой реплике); придумывать своё определение
   языка не нужно.
5. Стриминг присутствует с первой опубликованной версии плагина (1.3.0, 04.05.2026),
   а не появился вчера.

**Ограничения, которые придётся учесть (это не отменяет вывода, но меняет детали):**

- **Своего эндпоинтинга у Voxtral Realtime нет — VAD обязателен.** Плагин требует
  `@livekit/agents-plugin-silero`: если VAD не передан, он пытается загрузить Silero
  сам и падает с ошибкой, если пакета нет. По `END_OF_SPEECH` от VAD плагин шлёт
  `flushAudio()`, чтобы заставить сервер финализировать сегмент. Практический вывод:
  Silero — не опциональная оптимизация, а обязательная часть STT-конвейера, и порог
  тишины VAD (§3.3, 300–550 мс) напрямую определяет задержку финализации.
- **`targetStreamingDelayMs` в стриминге не работает.** Опция есть в `STTOptions` и в
  `updateOptions()`, но в `rt.connect()` передаются только `timeoutMs` (и опционально
  `audioFormat`, `serverUrl`, `httpHeaders`) — тип `RealtimeConnectOptions` другого
  не предусматривает. Серверная сессия поле `target_streaming_delay_ms` возвращает,
  то есть на стороне API настройка есть, но через Node-плагин 1.6.4 до неё не
  дотянуться. Утверждение PROJECT.md §2.2 «задержка настраивается вплоть до 200 мс»
  для Node-стека **неверно**: берём серверное значение по умолчанию.
- **`contextBias` в стриминге тоже не передаётся** — работает только в батчевом
  `_recognize()`. Это важно для итераций 6–7: подсказать распознавателю названия блюд
  из меню через contextBias не получится, вся тяжесть сопоставления ложится на
  `find_menu_items()` (алиасы + триграммы, спека 001).
- **`audioFormat` плагин не передаёт вообще**, полагаясь на серверный дефолт, и при
  этом шлёт 16 кГц моно PCM16. Совпадение с дефолтом сервера подтверждается только
  живым звонком — вносится в ручную проверку.
- **Стриминговый путь не покрыт автотестами апстрима**: `src/stt.test.ts` в пакете
  гоняет только батчевый режим (`{ streaming: false }`) и то лишь при наличии
  `MISTRAL_API_KEY`. Свои проверки на этот путь рассчитывать не на кого.

**Что осталось подтвердить живым звонком** (ручной тест, требует ключа, итерация 3):
фактическая задержка финализации, совпадение формата аудио с серверным дефолтом,
корректность определения языка на немецком, русском и английском.

### Переход STT на ElevenLabs Scribe v2 realtime (18.08.2026, PROJECT.md §2.2, §2.3)

**Причина замены — качество.** Владелец оценил распознавание Voxtral на живой речи как
недостаточное. Решение владельца; альтернативы (Deepgram, self-hosted Whisper) не
рассматривались, потому что ElevenLabs уже в стеке как TTS и не добавляет нового
субобработчика. На момент этой замены LLM ещё оставалась прежней; отдельной задачей
18.08.2026 она переведена на OpenAI, а Mistral runtime-зависимости удалены.

Разобран установленный `@livekit/agents-plugin-elevenlabs` **1.6.4**, `dist/stt.js`.
Проверяемые факты, каждый влияет на код:

- **Стриминг есть.** Модель `scribe_v2_realtime` даёт
  `super({ streaming: true, interimResults: true })`; пакетные `scribe_v1` и `scribe_v2`
  дают `streaming: false`. Поэтому `STT_MODEL` отвергает пакетные модели при старте
  (`agent/src/config.ts`): иначе несовместимость вскрылась бы на звонке.
- **Определение языка работает только при пустом `languageCode`.** Тогда плагин
  добавляет в URL `include_language_detection=true` и кладёт `language_code` ответа в

  `UserInputTranscribed.language`. Задать язык — значит выключить §4.1. Это
  зафиксировано комментарием в `buildStt`, потому что «пропущенный параметр» выглядит
  как недоработка и его легко «исправить».
- ⚠️ **Было исправлено 18.08.2026: при отсутствии `language_code` плагин подставлял
  `en`, а не `null`.** У Voxtral в этом случае был `null`. На живом звонке это привело

  ложный фолбэк языка на `en`» ниже.
- ⚠️ **`enable_logging` по умолчанию `true`.** Без явного `enableLogging: false`
  провайдер хранит аудио и расшифровки у себя, что запрещено PROJECT.md §0.4 и §11.3.
  Флаг выставлен и в STT, и в TTS.
- **Silero VAD больше не обязателен самому STT**, но остаётся в сессии: он даёт
  эндпоинтинг и прерывания вместе с turn-детектором. Серверный VAD ElevenLabs

  ограничение Voxtral, у которого `contextBias` в стриминге не работал. Не

- **Резидентность.** `ELEVENLABS_BASE_URL` теперь влияет и на STT: плагин превращает
  `https://` в `wss://` для realtime-соединения. Без него речь гостя уходит за пределы

### Патч `@livekit/agents-plugin-elevenlabs`: ложный фолбэк языка на `en` (18.08.2026)

**Инцидент на живом звонке:** гость говорил по-русски, агент с первой реплики отвечал
по-английски. `AGENT_DEFAULT_LANGUAGE` был немецким — то есть агент не остался на
стартовом языке, а **переключился на английский**, которого никто не произносил.

**Причина — в самом плагине**, `dist/stt.js`, метод `#processStreamEvent`:

```js
const languageCode = data.language_code ?? this.#language;
const normalizedLanguage = languageCode
  ? normalizeLanguage(languageCode)
  : normalizeLanguage("en");   // хардкод, а не null/undefined
```

Когда ElevenLabs не прислал `language_code` на конкретном событии (короткая или
неуверенно распознанная реплика), плагин молча подставляет `"en"`. Внешне это
неотличимо от настоящего распознавания английского — `UserInputTranscribed.language`
получает `"en"` в обоих случаях. А по §4.1 п.3 наш `LanguageTracker` фиксирует язык
сессии по **первой же** финальной реплике, даже если он отличается от стартового — это
осознанное и правильное поведение для настоящего распознавания, но оно же превращает
одну неудачную детекцию в необратимое решение на весь разговор.

**Почему не правили это в нашем коде.** Различить «ElevenLabs реально услышал English»
и «ElevenLabs не смог распознать и подставил en» на нашей стороне невозможно — оба
случая приходят одинаковым `language: "en"`. Информация о том, что детекция провалилась,
теряется внутри плагина безвозвратно. Патчить нашу логику (например, не доверять первому
`en`) означало бы закладывать в общие правила переключения знание о конкретном баге
конкретного провайдера — и заодно ломать реальных англоязычных звонящих, чья первая
короткая фраза тоже выглядела бы «подозрительной».

**Решение — патч пакета через `pnpm patch`.** Заменена ровно эта одна строка (в обоих
сборках, `dist/stt.js` и `dist/stt.cjs`, оба реально загружаются: ESM — рантаймом
агента, CJS — на случай require из другого инструментария):

```diff
- : normalizeLanguage("en");
+ : normalizeLanguage("");
```

`normalizeLanguage("")` возвращает `""` (пустую строку), а не «английский». Наш
`toLanguage()` в `agent/src/language.ts` уже трактует любую пустую/нераспознанную строку
как `null` → `LanguageTracker.observe()` её игнорирует, не сбрасывая серию и не
переключая язык. То есть однократный провал детекции ElevenLabs теперь ведёт себя
ровно как у Voxtral: реплику молча пропускаем, ждём следующую.

Патч зарегистрирован в `pnpm-workspace.yaml` (`patchedDependencies`) и хранится в
`patches/@livekit__agents-plugin-elevenlabs@1.6.4.patch`; применяется автоматически при
`pnpm install`. Риск: патч привязан к точной версии `1.6.4` и пишет только два поля в
одной функции — при обновлении плагина `pnpm install` явно откажется применить патч,
если исходный код изменился, и это не пройдёт незамеченным.

### Переключение языка в живой сессии (18.08.2026, PROJECT.md §4.1)

**Историческое решение, отменённое после живого инцидента с пустым языком STT.** Ниже
сохранено объяснение прежней реализации. Сейчас системный промпт один и не переключается;
событие `UserInputTranscribed` меняет только голосовой профиль и i18n-ресурсы.

**Точка подписки выбрана не произвольно.** В `@livekit/agents` 1.6.4
(`dist/voice/agent_activity.js`, метод `userTurnCompleted`) порядок такой:

```
const chatCtx = this.agent.chatCtx.copy();          // копия снимается ЗДЕСЬ
await this.agent.onUserTurnCompleted(chatCtx, …);   // хук вызывается ПОСЛЕ копии
… this.generateReply({ userMessage, chatCtx, … });  // отвечает по копии
```

Значит `agent.updateInstructions()`, вызванный из хука `onUserTurnCompleted`, изменил бы
`agent._chatCtx`, но не копию этого хода, — и новый язык подействовал бы только со
следующей реплики. Гость, перешедший на русский, услышал бы ещё один немецкий ответ.

Поэтому переключение висит на событии `UserInputTranscribed` с `isFinal === true`: оно
эмитится синхронно в `onFinalTranscript`, то есть до фиксации хода, а
`updateInstructions` для нереалтайм-LLM правит контекст синхронно. Новый промпт успевает
попасть в копию и действует уже на ответ той самой реплики.

Голос и язык TTS переключаются на том же событии через
`elevenlabs.TTS.updateOptions({ language, voiceId })` — плагин применяет их к следующему
соединению синтеза, поэтому уже начатая фраза договаривается прежним голосом. Это и есть
желаемое поведение: менять голос посреди предложения нельзя.

### Агент не отвечал после реплики гостя: `commit_strategy=manual` (18.08.2026)

**Симптом:** гость произносит фразу и замолкает — ничего не происходит. Когда он начинает
следующую фразу, она дописывается к той же незакрытой реплике. Появилось сразу после
перевода STT на ElevenLabs.

**Причина.** Плагин ElevenLabs выбирает стратегию коммита по наличию `serverVad`
(`dist/stt.js`):

```js
const commitStrategy = serverVad === undefined || serverVad === null ? "manual" : "vad";
```

В режиме `manual` команду `{ message_type: "input_audio_chunk", commit: true }` плагин
шлёт **только** получив `SpeechStream.FLUSH_SENTINEL` во входном потоке. Фреймворк его не
отправляет: `audio_recognition.js` флашит только VAD-поток и поток turn-детектора, но не
поток STT. Значит коммита не происходит никогда, `committed_transcript` не приходит, а
FINAL_TRANSCRIPT и END_OF_SPEECH порождаются только из него. Наружу идут одни
`partial_transcript` → INTERIM_TRANSCRIPT: реплика гостя не закрывается, ход не
фиксируется, ответ не генерируется, а следующая фраза продолжает ту же расшифровку.

Плагин Voxtral этой проблемы не имел: он держал внутри себя Silero и на `END_OF_SPEECH`
сам вызывал `connection.flushAudio()`, то есть коммитил сегмент собственными силами.
Разница в устройстве плагинов, а не в моделях.

**Решение:** `serverVad` задаётся всегда (`buildStt` в `agent/src/session.ts`), порог
тишины — `STT_VAD_SILENCE_THRESHOLD_MS` (умолчание 500 мс). Соединение уходит в
`commit_strategy=vad`, Scribe закрывает сегмент сам и присылает `committed_transcript`, из
которого плагин делает FINAL_TRANSCRIPT и END_OF_SPEECH.

Проверено разбором URL, который плагин строит для realtime-соединения (сеть не
использовалась, `wsConnect` подменён):

```
без serverVad:  model_id=scribe_v2_realtime  commit_strategy=manual  include_language_detection=true
с serverVad:    model_id=scribe_v2_realtime  commit_strategy=vad     include_language_detection=true  vad_silence_threshold_secs=0.5
```

⚠️ Цена решения: конец реплики теперь определяет серверный VAD ElevenLabs, а не только
`AGENT_MIN/MAX_ENDPOINTING_DELAY_MS`. Эти значения продолжают действовать поверх, но
основной порог ожидания — `STT_VAD_SILENCE_THRESHOLD_MS`. Именно его надо крутить, если
агент отвечает слишком рано или слишком поздно.

⚠️ Ошибочный диагноз, зафиксированный чтобы не повторять: сначала это же поведение было
принято за неработающее перебивание и «починено» настройкой
`turnHandling.interruption.resumeFalseInterruption`. Настройка к делу не относится и
откачена. Признак, по которому диагнозы различаются: при сломанном коммите агент не
отвечает **вообще**, даже когда гость молчит и не перебивает.

### Voxtral TTS в том же плагине — побочная находка проверки (15.08.2026)

**Историческая проверка.** Обнаружено при разборе прежнего пакета и сохранено как причина,
по которой текущий TTS целиком работает через ElevenLabs. На актуальный runtime и план
итерации 4 Voxtral больше не влияет.

- **TTS не стримит.** `class TTS extends tts.TTS` вызывает
  `super(SAMPLE_RATE, NUM_CHANNELS, { streaming: false })`. Утверждения PROJECT.md
  §2.2 («~90 мс, стриминг») и §3.3 («Voxtral TTS первый чанк ~90 мс») для Node-плагина
  **не подтверждаются**: реплика синтезируется целиком до начала воспроизведения, то
  есть задержка растёт с длиной реплики. Смягчение — `StreamAdapter` из
  `@livekit/agents`, который режет текст по предложениям, плюс жёсткое ограничение
  длины реплики из §14. Бюджет задержки §3.3 нужно пересчитать в итерации 4.
- **У TTS нет параметра языка вообще** — только `model`, `voice`, `refAudio`.
- **В типизированном списке голосов нет ни немецких, ни русских**: только `gb_*`,
  `fr_*`, `en_*` (английские и французские). Тип допускает произвольную строку
  (`MistralTTSVoices | string`), поэтому список может отставать от API — но плановая
  маршрутизация «de|en → Voxtral TTS» из §2.2 под вопросом. **Открытый вопрос
  итерации 4:** есть ли у Voxtral TTS немецкий голос. Проверяется по документации
  Mistral и живым запросом с ключом; если нет — немецкий тоже уходит на ElevenLabs,
  а Piper в итерации 14 должен закрыть и de, и ru.

### Приёмка спеки 001 на живой базе (15.08.2026)

### Совместимость реализаций TTS между собой (итерация 4, PROJECT.md §2.2)

у реализаций нет общей частоты дискретизации.

| | Voxtral (`plugin-mistralai`) | ElevenLabs (`plugin-elevenlabs`) |
|---|---|---|
| Частота | **24000 Гц**, жёстко зашита константой | из `encoding`; PCM только `pcm_16000`, `pcm_22050` (умолчание), `pcm_44100` |
| Стриминг | `{ streaming: false }` | `{ streaming: true }`, WebSocket |
| Параметр языка | отсутствует | `language` / `languageCode` |

`sampleRate` фиксируется в конструкторе `TTS` и определяет настройку источника звука во
фреймворке, то есть роутер обязан объявить **одну** частоту на все языки. Общего значения
у 24000 и {16000, 22050, 44100} нет.

Решения, заложенные в спеку 003:

- роутер объявляет единую частоту (`TTS_SAMPLE_RATE`, по умолчанию 24000 — натив Voxtral,
  чтобы основной языковой поток шёл без преобразования) и оборачивает реализации с другой
  частотой декоратором на `AudioResampler` из `@livekit/rtc-node` (нативный Sox;
  `close()` обязателен, иначе течёт файловый дескриптор);
- нестримящие реализации приводятся к стриминговым штатным `tts.StreamAdapter`
  (режет текст по предложениям), поэтому роутер объявляет `streaming: true`;
- порядок обёрток фиксирован: `StreamAdapter(ResamplingTts(provider))`;
- ресемплер не создаётся, если частоты совпадают, — лишнее преобразование это лишняя
  задержка. На фазе разработки, когда все три языка на ElevenLabs, преобразования нет вовсе.

Практическое замечание: на телефонии звук всё равно уходит в 8 кГц G.711 через
`livekit-sip`, поэтому разница в качестве выше 16 кГц значения не имеет — выбор частоты
диктуется отсутствием лишних преобразований, а не верностью звучания.

### Портал на Next.js 16: находки первой сборки (16.08.2026, спека 004)

- **`middleware.ts` в Next 16 объявлен устаревшим** — конвенция переименована в `proxy.ts`
  с экспортом функции `proxy`. Кроме имени есть содержательное отличие: **route segment
  config в этом файле запрещён вовсе**, `export const config = { runtime: … }` валит сборку
  с `Route segment config is not allowed in Proxy file`. Proxy всегда исполняется в
  Node-рантайме, поэтому оговорки про недоступность `process.env` в Edge к нему не относятся.
  `matcher` в `config` при этом допустим.
- **Через `NODE_OPTIONS` корневой `.env` не подгрузить.** Запуск `next build` командой
  `node --env-file-if-exists=../.env … next build` падает: Node запрещает этот флаг
  воркерам сборки (`ERR_WORKER_INVALID_EXEC_ARGV`). Приём, который работает у агента,
  для Next не годится. Решение — `process.loadEnvFile()` в `next.config.ts`: конфиг
  исполняется в каждом процессе Next, включая воркеры.
- **Biome теперь читает `.gitignore`** (`vcs.useIgnoreFile`). Без этого `biome check .`
  после первой сборки портала уходил в 42 тысячи диагностик по содержимому `.next/`.

### Тариф ElevenLabs и голоса из Voice Library (16.08.2026, первый живой прогон)

**Найдено при отладке молчащего агента.** На бесплатном тарифе ElevenLabs голоса из Voice
Library (`category: professional`, `sharing.status: copied`) **недоступны через API** —
и это проявляется по-разному в зависимости от протокола:

| Протокол | Поведение при недоступном голосе |
|---|---|
| HTTP `POST /v1/text-to-speech/{id}` | честный `402 payment_required`, `code: paid_plan_required` |
| WebSocket `multi-stream-input` | **ошибки нет**: контекст закрывается пустым `{audio: null, isFinal: true}` |

Агент использует именно WebSocket, поэтому сбой выглядел как полная тишина при внешне
здоровом логе — единственный след — `unexpected message received from elevenlabs tts` из
плагина (сообщение приходит для уже закрытого контекста). Проверено матрицей: немецкий
голос из библиотеки не отдаёт аудио ни на `eleven_flash_v2_5`, ни на `eleven_turbo_v2_5`,
ни на `eleven_multilingual_v2`; premade-голос на той же модели отдаёт 83 КБ.

Практические следствия:

- на бесплатном тарифе доступны только premade-голоса, все они англоязычные — немецкий они
  произносят через multilingual-модель, но с английским акцентом;
- **немецкий голос требует платного тарифа**; это входит в стоимость эксплуатации и должно
  быть решено до первого боевого ресторана (либо переходом на Piper из итерации 14);
- диагностика TTS не может опираться на молчание WebSocket: проверять голос нужно HTTP-запросом,
  он единственный возвращает внятную ошибку.

### Звонок с сайта не поднимал медиа: ICE без host-кандидатов (19.08.2026)

**Симптом.** Первый же звонок с лендинга: комната создавалась, участник входил
(`state: JOINED`), а через 15 секунд браузер писал `Encountered websocket error during
connection establishment` и `websocket closed { code: 1006 }`. Со стороны это выглядело как
проблема сигнального канала, но 1006 был следствием, а не причиной.

**Что показали логи `livekit-server`.** Сигнальный WebSocket отработал штатно: join прошёл,
пинги ходили. Упал медиатранспорт:

```
ice connection state change  transport: PUBLISHER  state: "failed"
leave { reason: "CONNECTION_TIMEOUT", action: "RESUME" }
```

Сводка по всем комнатам разделила случаи однозначно: `portal-test-*` доходят до
`PUBLISHER connected`, все `web-call-*` остаются в `checking` и закрываются.

**Причина.** Наборы ICE-кандидатов, которые прислал браузер, различались принципиально:

| | Портал (`localhost:3000`) | Сайт (`localhost:3001`) |
|---|---|---|
| `typ host` | `192.168.178.24`, `172.30.192.1`, IPv6 — 12 штук | нет ни одного |
| `typ srflx` | `92.208.241.48` | `92.208.241.48`, IPv6 |

Пока у origin нет разрешения на микрофон, Chrome не отдаёт локальные адреса, а подменяет
host-кандидаты именами mDNS `.local`. `livekit-server` mDNS не резолвит и такие кандидаты
выбрасывает. Остаётся только srflx на публичный адрес, а он до контейнера, опубликованного
на `127.0.0.1`, не маршрутизируется — соединиться не с чем.

Оба приложения вызывали `room.connect()` до `setMicrophoneEnabled(true)`, то есть собирали
кандидаты без разрешения. Портал работал только потому, что его origin получил разрешение
в один из прошлых звонков и Chrome его запомнил; `localhost:3001` — другой origin, и на
момент сбора кандидатов разрешения там не было ни разу.

**Решение.** `website/components/voice-call.tsx` получает микрофон `createLocalAudioTrack()`
до `room.connect()` и публикует готовую дорожку после подключения. К моменту сбора
кандидатов разрешение уже выдано, host-адреса видны, ICE соединяется. Побочный эффект
приятный: запрос микрофона возникает сразу после нажатия на трубку, а не в середине
«соединяю».

**Долг.** `portal/components/test-call.tsx` содержит ту же ошибку порядка и держится на
запомненном разрешении: в другом профиле браузера, после сброса разрешений или на новом
домене портальный звонок упадёт ровно так же. Не исправлено — правка портала выходила за
объём задачи; выносится отдельной задачей.

### Агент не входил в комнату: Silero грузился внутри джоба (20.08.2026)

**Симптом.** Медиа поднималось, звука не было, виджет через 12 секунд писал «Ассистент не
вошёл в разговор». В комнате портала участников двое (`portal-admin-*` и `agent-AJ_*`), в
комнате сайта — только браузер.

**Что показали логи.** LiveKit джоб назначал исправно:

```
assigned job to worker { agentName: "", jobType: "JT_ROOM", room: "web-call-…" }
```

Умирал сам процесс джоба:

```
23:59:28.540  received job request
23:59:29.064  agent_voice_mode_selected        ← 0.5 с: база и файлы отработали
              ...19.5 секунды тишины...
23:59:48.584  job process orphaned, shutting down
23:59:48.585  room not connect after job_entry was called after 10 seconds
```

**Причина.** В провале — `silero.VAD.load()`. Он вызывался внутри `entry`, то есть уже во
время звонка. Инициализация нативного onnxruntime блокирует event loop дочернего процесса,
тот перестаёт отвечать на пинги родителя, и срабатывает `ORPHANED_TIMEOUT` — 15 секунд,
зашитые в `@livekit/agents/dist/ipc/job_proc_lazy_main.js`. Процесс убивал себя раньше, чем
доходил до `session.start()`, поэтому в комнате не появлялся никогда.

Функции `prewarm` в проекте не было вовсе: в `defineAgent` передавался только `entry`, хотя
комментарий в `agent/src/index.ts` уже ссылался на неё. `numIdleProcesses: 1` прогревает
форк процесса — импорты модулей, — но не модель.

**Это не проблема сайта.** Первый pipeline-звонок после `pnpm agent:dev` падал так же и из
портала; прежние успехи портала — попадания в 15 секунд на прогретом файловом кеше ОС.
Граница проходила прямо по рабочему диапазону, поэтому дефект выглядел как случайный.

**Решение.** Загрузка VAD перенесена в `prewarm(proc)`: она выполняется в простаивающем
процессе до звонка, где блокировка event loop никого не задевает, а `entry` берёт готовый
промис. `??=` в `entry` оставлен как страховка на случай процесса без прогрева. Прогрев
безусловный, в том числе для realtime-режима, который VAD не использует: он идёт вне звонка
и стоит только памяти простаивающего процесса.

**Про `agentName`.** Пустое имя — правильная настройка, а не причина: именно из-за него
LiveKit диспатчит воркер в каждую новую комнату (`portal/lib/livekit.ts`,
`website/lib/livekit.ts`). Заданное имя отключило бы автодиспатч и потребовало бы явного
dispatch-запроса на каждую комнату.
