### Стриминг Voxtral Realtime в `@livekit/agents-plugin-mistralai` (итерация 3, PROJECT.md §2.3)

**Статус: проверено 15.08.2026. Ответ — стриминг ЕСТЬ. Работаем как задумано,
кастомный STT-плагин и Deepgram не нужны.**

Что проверялось: `@livekit/agents-plugin-mistralai` **1.6.4** (опубликована 14.08.2026,
последняя стабильная), `@livekit/agents` 1.6.4, транзитивно `@mistralai/mistralai` 2.6.3.
Метод — статический разбор исходников пакета (пакет публикует `src/`, не только `dist/`).
Живой звонок с реальным ключом не выполнялся: реальные ключи и вызовы внешних API
запрещены в автоматической проверке (AGENTS.md §4), это шаг ручного теста.

**Доказательства:**

1. `STT` объявляет возможности динамически, по имени модели:
   `super({ streaming: isRealtime(model), interimResults: isRealtime(model) })`,
   где `isRealtime` = имя модели содержит `realtime`. Для
   `voxtral-mini-transcribe-realtime-2602` (модель из PROJECT.md §2 — присутствует
   в union `MistralSTTModels`, имя верное) это даёт `streaming: true`.
2. `STT.stream()` возвращает `SpeechStream`, работающий через
   `RealtimeTranscription` из `@mistralai/mistralai/extra/realtime`. Это настоящий
   WebSocket: модуль импортирует `ws`, соединение живёт как `RealtimeConnection`
   с `sendAudio()` / `flushAudio()` / `endAudio()` и асинхронным итератором событий.
   Для нереалтаймовой модели `stream()` бросает исключение с внятным текстом.
3. Промежуточные результаты приходят: событие `transcription.text.delta` →
   `INTERIM_TRANSCRIPT`, событие `transcription.done` → `FINAL_TRANSCRIPT`.
   Аудио отправляется чанками по 50 мс, 16 кГц моно PCM16.
4. **Язык определяется сервером и сообщается клиенту** — событие
   `transcription.language` c полем `audioLanguage`. Это ровно то, на чём построен
   §4.1 (фиксация языка сессии по первой реплике); придумывать своё определение
   языка не нужно.
5. Стриминг присутствует с первой опубликованной версии плагина (1.3.0, 04.05.2026),
   а не появился вчера.

**Ограничения, которые придётся учесть (это не отменяет вывода, но меняет детали):**

- **Своего эндпоинтинга у Voxtral Realtime нет — VAD обязателен.** Плагин требует
  `@livekit/agents-plugin-silero`: если VAD не передан, он пытается загрузить Silero
  сам и падает с ошибкой, если пакета нет. По `END_OF_SPEECH` от VAD плагин шлёт
  `flushAudio()`, чтобы заставить сервер финализировать сегмент. Практический вывод:
  Silero — не опциональная оптимизация, а обязательная часть STT-конвейера, и порог
  тишины VAD (§3.3, 300–550 мс) напрямую определяет задержку финализации.
- **`targetStreamingDelayMs` в стриминге не работает.** Опция есть в `STTOptions` и в
  `updateOptions()`, но в `rt.connect()` передаются только `timeoutMs` (и опционально
  `audioFormat`, `serverUrl`, `httpHeaders`) — тип `RealtimeConnectOptions` другого
  не предусматривает. Серверная сессия поле `target_streaming_delay_ms` возвращает,
  то есть на стороне API настройка есть, но через Node-плагин 1.6.4 до неё не
  дотянуться. Утверждение PROJECT.md §2.2 «задержка настраивается вплоть до 200 мс»
  для Node-стека **неверно**: берём серверное значение по умолчанию.
- **`contextBias` в стриминге тоже не передаётся** — работает только в батчевом
  `_recognize()`. Это важно для итераций 6–7: подсказать распознавателю названия блюд
  из меню через contextBias не получится, вся тяжесть сопоставления ложится на
  `find_menu_items()` (алиасы + триграммы, спека 001).
- **`audioFormat` плагин не передаёт вообще**, полагаясь на серверный дефолт, и при
  этом шлёт 16 кГц моно PCM16. Совпадение с дефолтом сервера подтверждается только
  живым звонком — вносится в ручную проверку.
- **Стриминговый путь не покрыт автотестами апстрима**: `src/stt.test.ts` в пакете
  гоняет только батчевый режим (`{ streaming: false }`) и то лишь при наличии
  `MISTRAL_API_KEY`. Свои проверки на этот путь рассчитывать не на кого.

**Что осталось подтвердить живым звонком** (ручной тест, требует ключа, итерация 3):
фактическая задержка финализации, совпадение формата аудио с серверным дефолтом,
корректность определения языка на немецком, русском и английском.

### Voxtral TTS в том же плагине — побочная находка проверки (15.08.2026)

Обнаружено при разборе пакета; **влияет на итерацию 4**, поэтому зафиксировано сразу.

- **TTS не стримит.** `class TTS extends tts.TTS` вызывает
  `super(SAMPLE_RATE, NUM_CHANNELS, { streaming: false })`. Утверждения PROJECT.md
  §2.2 («~90 мс, стриминг») и §3.3 («Voxtral TTS первый чанк ~90 мс») для Node-плагина
  **не подтверждаются**: реплика синтезируется целиком до начала воспроизведения, то
  есть задержка растёт с длиной реплики. Смягчение — `StreamAdapter` из
  `@livekit/agents`, который режет текст по предложениям, плюс жёсткое ограничение
  длины реплики из §14. Бюджет задержки §3.3 нужно пересчитать в итерации 4.
- **У TTS нет параметра языка вообще** — только `model`, `voice`, `refAudio`.
- **В типизированном списке голосов нет ни немецких, ни русских**: только `gb_*`,
  `fr_*`, `en_*` (английские и французские). Тип допускает произвольную строку
  (`MistralTTSVoices | string`), поэтому список может отставать от API — но плановая
  маршрутизация «de|en → Voxtral TTS» из §2.2 под вопросом. **Открытый вопрос
  итерации 4:** есть ли у Voxtral TTS немецкий голос. Проверяется по документации
  Mistral и живым запросом с ключом; если нет — немецкий тоже уходит на ElevenLabs,
  а Piper в итерации 14 должен закрыть и de, и ru.

### Приёмка спеки 001 на живой базе (15.08.2026)

Реализацию спеки 001 Codex выполнил в контейнере без Docker, без npm registry и на
Node 20, поэтому ничего не запускал. Прогон на машине владельца 15.08.2026 состоялся;
результаты и найденные дефекты:

**Что подтвердилось на живом PostgreSQL 18.6:**

- миграции 001–004 применяются, схема создаётся полностью; `db:seed` работает и идемпотентен;
- **двойное бронирование невозможно** (PROJECT.md §13). Проверено тремя способами:
  детерминированный тест — вторая транзакция висит на `FOR UPDATE`, пока первая не
  закоммитит, после чего получает `no_table_available` (SQLSTATE 45001); стресс —
  из 10 параллельных вызовов проходит ровно один; прямая вставка мимо функции
  отвергается ограничением `reservations_no_overlap` (SQLSTATE 23P01);
- **перепродажа слота самовывоза невозможна** (§13): при `pickup_slot_capacity = 1`
  из двух параллельных заказов проходит один, второй получает `slot_full` (45002);
  номер заказа — 4 цифры, сумма считается базой верно.

**Дефекты, найденные и исправленные:**

1. **`scripts/db/migrate.ts` молча не работал на Windows.** Условие запуска было записано
   как `import.meta.url === \`file://${process.argv[1]}\``. На Windows `argv[1]` — это
   `C:\путь\migrate.ts`, а `import.meta.url` — `file:///C:/путь/migrate.ts`; равенства
   не возникает никогда. `pnpm db:migrate` завершался с кодом 0, не применив ни одной
   миграции. Исправлено на `pathToFileURL(process.argv[1]).href`.
2. **ESM не был объявлен.** В корневом `package.json` отсутствовал `"type": "module"`,
   хотя весь код написан на ESM (top-level await, `import.meta`). При `module: NodeNext`
   это делало все файлы CommonJS — 14 ошибок компиляции.
3. **Две ошибки типов** под `exactOptionalPropertyTypes` в паре
   `rolePasswords()` / `setRolePasswords()`; их находит только TypeScript 7.
4. **`biome.json` был написан под Biome 2.2** и использовал устаревшее
   `linter.rules.recommended`. Мигрирован; при этом `biome migrate` предлагает
   `preset: "none"`, что **выключает все правила** — заменено на `preset: "recommended"`.
5. Порт dev-контейнера перенесён с 5432 на **55432**: на машине владельца стандартный порт
   занят нативной установкой PostgreSQL, и подключение молча уходило туда (ошибка
   аутентификации в русской локали выдала чужой сервер).

**Тестовая матрица дописана 15.08.2026.** Codex оставил 4 файла и 6 смоук-тестов, ни один
из которых не вызывал бизнес-логику; тестов на гонку не было вовсе. Матрица доведена до

### Совместимость реализаций TTS между собой (итерация 4, PROJECT.md §2.2)

Выяснено при подготовке спеки 003 разбором установленных плагинов 1.6.4.
**Целевая схема §2.2 «de|en → Voxtral, ru → Piper/ElevenLabs» не собирается «в лоб»** —
у реализаций нет общей частоты дискретизации.

| | Voxtral (`plugin-mistralai`) | ElevenLabs (`plugin-elevenlabs`) |
|---|---|---|
| Частота | **24000 Гц**, жёстко зашита константой | из `encoding`; PCM только `pcm_16000`, `pcm_22050` (умолчание), `pcm_44100` |
| Стриминг | `{ streaming: false }` | `{ streaming: true }`, WebSocket |
| Параметр языка | отсутствует | `language` / `languageCode` |

`sampleRate` фиксируется в конструкторе `TTS` и определяет настройку источника звука во
фреймворке, то есть роутер обязан объявить **одну** частоту на все языки. Общего значения
у 24000 и {16000, 22050, 44100} нет.

Решения, заложенные в спеку 003:

- роутер объявляет единую частоту (`TTS_SAMPLE_RATE`, по умолчанию 24000 — натив Voxtral,
  чтобы основной языковой поток шёл без преобразования) и оборачивает реализации с другой
  частотой декоратором на `AudioResampler` из `@livekit/rtc-node` (нативный Sox;
  `close()` обязателен, иначе течёт файловый дескриптор);
- нестримящие реализации приводятся к стриминговым штатным `tts.StreamAdapter`
  (режет текст по предложениям), поэтому роутер объявляет `streaming: true`;
- порядок обёрток фиксирован: `StreamAdapter(ResamplingTts(provider))`;
- ресемплер не создаётся, если частоты совпадают, — лишнее преобразование это лишняя
  задержка. На фазе разработки, когда все три языка на ElevenLabs, преобразования нет вовсе.

Практическое замечание: на телефонии звук всё равно уходит в 8 кГц G.711 через
`livekit-sip`, поэтому разница в качестве выше 16 кГц значения не имеет — выбор частоты
диктуется отсутствием лишних преобразований, а не верностью звучания.

### Портал на Next.js 16: находки первой сборки (16.08.2026, спека 004)

- **`middleware.ts` в Next 16 объявлен устаревшим** — конвенция переименована в `proxy.ts`
  с экспортом функции `proxy`. Кроме имени есть содержательное отличие: **route segment
  config в этом файле запрещён вовсе**, `export const config = { runtime: … }` валит сборку
  с `Route segment config is not allowed in Proxy file`. Proxy всегда исполняется в
  Node-рантайме, поэтому оговорки про недоступность `process.env` в Edge к нему не относятся.
  `matcher` в `config` при этом допустим.
- **Через `NODE_OPTIONS` корневой `.env` не подгрузить.** Запуск `next build` командой
  `node --env-file-if-exists=../.env … next build` падает: Node запрещает этот флаг
  воркерам сборки (`ERR_WORKER_INVALID_EXEC_ARGV`). Приём, который работает у агента,
  для Next не годится. Решение — `process.loadEnvFile()` в `next.config.ts`: конфиг
  исполняется в каждом процессе Next, включая воркеры.
- **Biome теперь читает `.gitignore`** (`vcs.useIgnoreFile`). Без этого `biome check .`
  после первой сборки портала уходил в 42 тысячи диагностик по содержимому `.next/`.

### Тариф ElevenLabs и голоса из Voice Library (16.08.2026, первый живой прогон)

**Найдено при отладке молчащего агента.** На бесплатном тарифе ElevenLabs голоса из Voice
Library (`category: professional`, `sharing.status: copied`) **недоступны через API** —
и это проявляется по-разному в зависимости от протокола:

| Протокол | Поведение при недоступном голосе |
|---|---|
| HTTP `POST /v1/text-to-speech/{id}` | честный `402 payment_required`, `code: paid_plan_required` |
| WebSocket `multi-stream-input` | **ошибки нет**: контекст закрывается пустым `{audio: null, isFinal: true}` |

Агент использует именно WebSocket, поэтому сбой выглядел как полная тишина при внешне
здоровом логе — единственный след — `unexpected message received from elevenlabs tts` из
плагина (сообщение приходит для уже закрытого контекста). Проверено матрицей: немецкий
голос из библиотеки не отдаёт аудио ни на `eleven_flash_v2_5`, ни на `eleven_turbo_v2_5`,
ни на `eleven_multilingual_v2`; premade-голос на той же модели отдаёт 83 КБ.

Практические следствия:

- на бесплатном тарифе доступны только premade-голоса, все они англоязычные — немецкий они
  произносят через multilingual-модель, но с английским акцентом;
- **немецкий голос требует платного тарифа**; это входит в стоимость эксплуатации и должно
  быть решено до первого боевого ресторана (либо переходом на Piper из итерации 14);
- диагностика TTS не может опираться на молчание WebSocket: проверять голос нужно HTTP-запросом,
  он единственный возвращает внятную ошибку.
