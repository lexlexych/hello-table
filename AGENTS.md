# AGENTS.md — правила работы над проектом

Единый свод правил для агента, который ведёт разработку. Правила **одинаковы для Claude Code и
Codex**: проект можно вести целиком из любого из них. Внутри одной задачи инструменты не
смешиваются — задачу от начала до конца делает один агент.

Codex читает этот файл автоматически; Claude Code приходит сюда по ссылке из `CLAUDE.md`.

## 1. О проекте и живая документация

Голосовой ИИ-агент для ресторана: приём звонков на немецком, русском и английском;
бронирование столиков, заказы на самовывоз, ответы по меню, оформление обратного звонка;
веб-портал с ролями администратора и оператора. Стек: TypeScript-монорепо (pnpm),
LiveKit + OpenAI (LLM) + ElevenLabs (STT/TTS), n8n как слой инструментов, PostgreSQL,
Next.js.

**Источник истины — `docs/PROJECT.md`.** Это живой документ: полное техническое задание,
архитектура, модель данных, итерации (§12) и приёмочные проверки (§13). Правила работы с ним:

- Читай его перед началом любой задачи — он мог измениться с прошлой сессии.
- Если реальность разошлась с документом (изменилось решение, версия, схема) — обнови
  документ **в том же изменении** и зафиксируй причину в `docs/architecture.md`.
- Чек-лист итераций (§12) отмечается только по факту выполнения.

Владелец проекта — соло-разработчик, он эксплуатирует систему один и должен понимать каждую
строчку. Скорость менее важна, чем его понимание.

## 2. Как работает агент

Отдельного этапа спецификации нет. **Каждая задача — один полный цикл**: разобраться,
привести документацию в соответствие, реализовать, проверить, записать в журнал.

1. **Разобраться.** Прочитать `docs/PROJECT.md`, разделы `docs/architecture.md` по теме задачи и
   профильный навык-чеклист (§7). Понять, к какой итерации §12 относится задача. Если непонятно —
   спросить, не угадывать.
2. **Объяснить план словами и дождаться подтверждения.** Какие файлы создаются и меняются, зачем,
   какие альтернативы рассматривались и почему выбрана эта; дерево изменений. Явное подтверждение
   владельца в диалоге — это и есть одобрение плана; отдельный документ-спецификация не пишется.
3. **Привести документацию в соответствие.** Если задача меняет то, что описано в `docs/`, —
   правка документа входит в ту же задачу, а не откладывается (см. §3).
4. **Реализовать.** Строго в объёме согласованного плана. Расширение объёма по ходу — только
   с согласия владельца.
5. **Проверить** по правилам §4. Провалившийся обязательный автотест блокирует завершение задачи.
6. **Записать результат.** Обязательно — запись в `docs/CHANGELOG.md`. По необходимости — решение
   с обоснованием в `docs/architecture.md`, инструкция ручной проверки в `docs/manual-tests.md`,
   отметка итерации в `docs/PROJECT.md` §12 (только если итерация закрыта целиком; частичное
   выполнение помечается `[~]` с перечнем того, что осталось).
7. **Объяснить ключевые решения владельцу.** Не пересказывать очевидное — объяснять то, что через
   месяц будет неочевидно. В конце сказать, что делать дальше и какие ручные проверки на нём.

## 3. Документация: что куда пишется

Разграничение жёсткое — одна и та же информация не дублируется в двух файлах.

| Файл | Что туда пишется |
|---|---|
| `docs/PROJECT.md` | Техническое задание и текущее состояние: концепция, архитектура, схема данных, контракты, экраны портала, чек-лист итераций §12, приёмочные проверки §13 |
| `docs/architecture.md` | **Почему так**: решения с обоснованием, точные версии с датой проверки, результаты обязательных технических проверок |
| `docs/CHANGELOG.md` | **Что именно изменено**: журнал работ, запись на каждую задачу |
| `docs/manual-tests.md` | Проверки, которые выполняет человек: предусловия → шаги → ожидаемый результат → что записать |
| `docs/tool-contracts.md` | Контракты инструментов агента (см. навык `agent-tools`) |
| `docs/runbook.md` | Эксплуатация: заполняется в итерации 15 |
| `specs/` | **Архив.** Спецификации итераций 2–4, 9, 11, написанные при прежнем двухэтапном процессе. Новые файлы туда не добавляются, статусы в них не меняются |

## 4. Правила тестирования (жёсткие)

- Тестраннер — vitest. Каждая Postgres-функция и каждый инструмент агента покрыты тестами.
- Автотесты проверяют **только то, что работает в локальном окружении**: чистые функции,
  zod-схемы, Postgres в локальном Docker, HTTP-обвязку с моками.
- **Запрещено в автотестах:**
  - реальные API-ключи (в том числе из `.env` разработчика);
  - реальные сетевые вызовы внешних API — OpenAI, ElevenLabs, LiveKit Cloud, Telegram,
    любые другие;
  - любые вызовы LLM-моделей.

  Внешние сервисы — только моки, фейки и фикстуры.
- Всё, что требует реальных ключей, сети или LLM, тестируется человеком вручную по
  `docs/manual-tests.md`. Инструкция обязана быть выполнимой без чтения кода: предусловия → шаги →
  ожидаемый результат → что записать.

### 4.1 Прогон в контейнерах

- Compose-проект запускается с **уникальным именем** (`-p`), чтобы не задеть чужие контейнеры.
- Переменные окружения — из **отдельного временного `--env-file`** с фиктивными значениями.
  Нельзя позволять Compose автоматически подхватывать корневой `.env` разработчика.
- Фиктивный ключ сам по себе не блокирует сеть: внешние вызовы должны быть невозможны по
  устройству теста (мок, фейк, отсутствие сетевого доступа), а не по неверному ключу.
- Убирать за собой **только свои** контейнеры, тома и сети.
- Локальная база для тестов — PostgreSQL в Docker на порту 55432 (обоснование —
  `docs/architecture.md`).

### 4.2 Честность результата

- Не подменять провалившийся автотест ручной проверкой и не ослаблять тест, чтобы он позеленел.
- Если обязательная локальная проверка невыполнима в текущем окружении — это блокирует объявление
  задачи готовой; причина пишется в `docs/CHANGELOG.md`, а не замалчивается.
- В отчёте владельцу указывается фактический результат прогона: какая команда запускалась и что
  она вернула.

## 5. Технические правила

(дублируют `docs/PROJECT.md` §0.4; при расхождении PROJECT.md главнее)

- Весь стек — TypeScript: Node 24 LTS (агент), Next.js 16 (портал).
- `strict: true` везде, `any` запрещён. Ошибки типов блокирующие.
- Монорепо pnpm workspaces. Общие типы и zod-схемы — только в `packages/contracts`;
  дублировать их в агенте или портале запрещено.
- Линт и форматирование — biome.
- Конфиг из переменных окружения валидируется zod при старте. При некорректном конфиге
  приложение падает, а не работает наполовину.
- Персональные данные не логируются: ни имён, ни телефонов, ни транскриптов. Аудио не
  записывается нигде, egress не разворачивается.
- Бизнес-логика бронирования и заказов — только в Postgres-функциях (PROJECT.md §3.4).
  Не в TypeScript и не в Function-узлах n8n.
- Версии зависимостей фиксируются точно, lock-файл коммитится. Таблица «что установлено
  и на какую дату проверено» — в `docs/architecture.md`.

## 6. Чего не делать никогда

- Не выполнять несколько итераций за одну сессию.
- Не добавлять запись аудио или хранение транскриптов разговоров.
- Не подключать сервисы за пределами ЕС без явного согласия владельца.
- Не рефакторить то, о чём не просили.
- Не создавать файлы «на будущее» и заглушки без реализации.
- Не помещать бизнес-логику бронирования в промпт LLM или в JavaScript n8n.

## 7. Навыки-чеклисты

Канонические чек-листы лежат в `.claude/skills/` — это единый проектный источник. Перед работой
в соответствующей области агент **обязан** прочитать нужный файл и следовать ему как
обязательному:

| Область | Файл |
|---|---|
| Схема БД, миграции, функции, роли | `.claude/skills/db-migrations/SKILL.md` |
| Инструменты агента (tool calling) | `.claude/skills/agent-tools/SKILL.md` |
| Workflow n8n | `.claude/skills/n8n-workflows/SKILL.md` |
| Проверка голосового агента | `.claude/skills/voice-testing/SKILL.md` |
| Деплой и инфраструктура | `.claude/skills/deployment/SKILL.md` |

В Claude Code навыки срабатывают автоматически. Для Codex в `.agents/skills/` лежат адаптеры с
теми же именами — они отправляют к каноническому файлу; правила в них не копируются.

## 8. Структура репозитория

Целевая структура — PROJECT.md §9. Файлы исходников появляются только в своих итерациях —
пустые заглушки не создаются.
