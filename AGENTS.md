# AGENTS.md — правила работы агентов в проекте

Единый свод правил для обоих агентов — **Claude Code** и **Codex**. Codex читает этот файл
автоматически; Claude Code приходит сюда по ссылке из `CLAUDE.md`.

## 1. О проекте

Голосовой ИИ-агент для ресторана: приём звонков на немецком, русском и английском;
бронирование столиков, заказы на самовывоз, ответы по меню, оформление обратного звонка;
веб-портал с ролями администратора и оператора. Стек: TypeScript-монорепо (pnpm),
LiveKit + Mistral (Voxtral/Large 3), n8n как слой инструментов, PostgreSQL, Next.js.

**Источник истины — `docs/PROJECT.md`.** Это живой документ: полное техническое задание,
архитектура, модель данных, итерации (§12) и приёмочные проверки (§13). Правила работы с ним:

- Читай его перед началом любой задачи — он мог измениться с прошлой сессии.
- Если реальность разошлась с документом (изменилось решение, версия, схема) — обнови
  документ в том же изменении и зафиксируй причину в `docs/architecture.md`.
- Чек-лист итераций (§12) отмечается только по факту выполнения.

## 2. Роли агентов

| Агент | Этап | Что делает |
|---|---|---|
| **Claude Code** | Спецификация (`/spec`) | Детальный план реализации: файлы, контракты, схемы, план тестирования, критерии приёмки. Предлагает следующие шаги. Код приложения не пишет. |
| **Codex** | Реализация (`/impl`) | Пишет код строго по спеке, пишет автотесты, готовит инструкции ручного тестирования и отчёт о реализации. |

Владелец проекта — соло-разработчик, он эксплуатирует систему один и должен понимать
каждую строчку. Он читает спеку перед запуском `/impl`; запуск `/impl` владельцем — это
и есть одобрение плана (подтверждение из §0.1 PROJECT.md).

## 3. Процесс

Каждая задача проходит два этапа.

### Этап 1 — спецификация (Claude Code, команда `/spec`)

1. Прочитать `docs/PROJECT.md` и текущее состояние репозитория (включая прошлые спеки).
2. Создать `specs/NNN-<slug>/spec.md` по `specs/TEMPLATE.md` (NNN — следующий свободный
   номер, слитная нумерация по всем спекам).
3. Спека обязана содержать: цель, объём, детальное техническое решение (какие файлы
   создаются и меняются, контракты, схемы данных, сигнатуры, SQL), пошаговый план,
   план тестирования (см. §4), критерии приёмки, риски и предложения следующих шагов.
4. Статус готовой спеки — `ready-for-impl`. Одна спека ≈ одна итерация из §12 PROJECT.md
   или её связная часть; несколько итераций в одну спеку не сваливать.

### Этап 2 — реализация (Codex, команда `/impl`)

1. Codex читает `AGENTS.md`, затем `specs/NNN-<slug>/spec.md` целиком, затем профильные
   чек-листы из `.claude/skills/` (см. §7).
2. Реализует **строго по спеке**. Отступление допустимо только если спека неисполнима —
   тогда оно фиксируется в `report.md` с обоснованием, а спека правится.
3. Пишет автотесты по правилам §4.
4. Для того, что автотестами не покрывается, пишет `specs/NNN-<slug>/manual-tests.md` —
   пошаговую инструкцию для человека: подготовка, действия, ожидаемый результат.
5. Пишет `specs/NNN-<slug>/report.md`: что сделано, отклонения от спеки, как запускать,
   результаты прогона тестов.
6. Статус спеки → `implemented` ставится после приёмки (её выполняет Claude Code в `/impl`).

Статусы спеки: `draft → ready-for-impl → in-progress → implemented → verified`
(`verified` — после ручного тестирования владельцем).

## 4. Правила тестирования (жёсткие)

- Тестраннер — vitest. Каждая Postgres-функция и каждый инструмент агента покрыты тестами.
- Автотесты проверяют **только то, что работает в локальном окружении**: чистые функции,
  zod-схемы, Postgres в локальном Docker, HTTP-обвязку с моками.
- **Запрещено в автотестах:**
  - реальные API-ключи (в том числе из `.env` разработчика);
  - реальные сетевые вызовы внешних API — Mistral, ElevenLabs, LiveKit Cloud, Telegram,
    любые другие;
  - любые вызовы LLM-моделей.
  Внешние сервисы — только моки, фейки и фикстуры.
- Всё, что требует реальных ключей, сети или LLM, тестируется человеком вручную по
  `manual-tests.md` соответствующей спеки. Инструкция обязана быть выполнимой без чтения
  кода: предусловия → шаги → ожидаемый результат → что записать.

## 5. Технические правила

(перенесены из §0.4 PROJECT.md; при расхождении PROJECT.md главнее)

- Весь стек — TypeScript: Node 24 LTS (агент), Next.js 16 (портал).
- `strict: true` везде, `any` запрещён. Ошибки типов блокирующие.
- Монорепо pnpm workspaces. Общие типы и zod-схемы — только в `packages/contracts`;
  дублировать их в агенте или портале запрещено.
- Линт и форматирование — biome.
- Конфиг из переменных окружения валидируется zod при старте. При некорректном конфиге
  приложение падает, а не работает наполовину.
- Персональные данные не логируются: ни имён, ни телефонов, ни транскриптов. Аудио не
  записывается нигде, egress не разворачивается.
- Бизнес-логика бронирования и заказов — только в Postgres-функциях (PROJECT.md §3.4).
  Не в TypeScript и не в Function-узлах n8n.
- Версии зависимостей фиксируются точно, lock-файл коммитится. Таблица «что установлено
  и на какую дату проверено» — в `docs/architecture.md`.

## 6. Чего не делать никогда

- Не выполнять несколько итераций за одну сессию/спеку.
- Не добавлять запись аудио или хранение транскриптов разговоров.
- Не подключать сервисы за пределами ЕС без явного согласия владельца.
- Не рефакторить то, о чём не просили.
- Не создавать файлы «на будущее» и заглушки без реализации.
- Не помещать бизнес-логику бронирования в промпт LLM или в JavaScript n8n.

## 7. Навыки-чеклисты

В `.claude/skills/` лежат пять обязательных чек-листов. Для Claude Code они срабатывают
автоматически; **Codex обязан прочитать соответствующий SKILL.md перед работой в области**:

| Область | Файл |
|---|---|
| Схема БД, миграции, функции, роли | `.claude/skills/db-migrations/SKILL.md` |
| Инструменты агента (tool calling) | `.claude/skills/agent-tools/SKILL.md` |
| Workflow n8n | `.claude/skills/n8n-workflows/SKILL.md` |
| Проверка голосового агента | `.claude/skills/voice-testing/SKILL.md` |
| Деплой и инфраструктура | `.claude/skills/deployment/SKILL.md` |

## 8. Структура репозитория

Целевая структура — PROJECT.md §9. Сейчас создан каркас: каталоги, конфигурация и

пустые заглушки не создаются.
