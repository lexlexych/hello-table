# Портал

Next.js 16 (App Router), Node 24. Три раздела: тестовый звонок из браузера,
столики и меню (17.08.2026, PROJECT.md §7.3 пп. 6–7). Дашборд, брони, заказы, коллбэки,
часы и настройки — итерации 9–10.

## Что делает страница звонка

Портал **не** реализует цепочку STT → LLM → TTS. Он выдаёт токен LiveKit и подключает
микрофон к новой комнате; воркер агента входит в неё сам (в его `WorkerOptions` нет
`agentName`, поэтому LiveKit диспатчит его в каждую новую комнату). Распознавание речи,
ответ модели и синтез происходят в `agent/`.

```
браузер /test-call ──POST /api/test-call/token──► портал (выпуск AccessToken)
        └────────── wss ──────────► livekit ◄────────── agent worker
             голос вверх, речь агента вниз, транскрипт топиком lk.transcription
```

## Справочники: столики и меню

`/tables` и `/menu` читают и правят базу напрямую (PROJECT.md §3.4 это разрешает:
бизнес-логика брони живёт в функциях, справочники — обычные таблицы).

- Смотрят обе роли, редактирует только администратор. У оператора кнопки записи не
  отрисованы, а маршруты `/api/tables/*` и `/api/menu/*` независимо отвечают ему 403.
- Удаление настоящее, а не флаг: `DELETE` разрешён роли `portal_app` точечно на
  `restaurant_tables`, `menu_categories`, `menu_items`. Строку, на которую кто-то
  ссылается (столик с бронью, блюдо из заказа, непустая категория), база не отдаёт —
  ответ 409 `in_use`, и портал предлагает выключить вместо удаления.
- Цена вводится в евро (запятая или точка), хранится в центах, показывается
  `Intl.NumberFormat("de-DE")`. Веганское блюдо автоматически становится
  вегетарианским — этого требует `CHECK` в миграции 003.

## Брони столиков на день

Исключение из абзаца выше: сами брони портал пишет не прямым SQL, а функциями
`book_table_for_day` и `cancel_table_booking` (PROJECT.md §5.3).

- Вверху `/tables` — выбор дня: «Сегодня», «Завтра», ещё четыре дня и календарь.
  День живёт в адресной строке (`/tables?date=2026-08-22`), поэтому ссылку можно
  переслать, а перезагрузка не сбрасывает выбор. «Сегодня» считается по таймзоне
  ресторана, а не сервера (`portal/lib/day.ts`).
- Бронь занимает столик **с указанного времени до местной полуночи** — на один
  столик в дне приходится ровно одна бронь. Записывается она в ту же таблицу
  `reservations`, что и телефонные брони, поэтому голосовой агент занятый столик
  гостям не предложит.
- Бронировать и снимать бронь могут обе роли (§7.2), справочник столиков по-прежнему
  правит только администратор.
- Прошедший день открывается только на просмотр: кнопок брони нет, а функция базы
  такую попытку отвергает кодом `45006`.
- Снятие брони — это `status = 'cancelled'`, а не удаление: `DELETE` на
  `reservations` не выдан никому, персональные данные убирает
  `purge_expired_personal_data()`.

## Запуск

Нужны заполненный корневой `.env` (секции Postgres, LiveKit, OpenAI, ElevenLabs, Портал)
и поднятая база. Для тестового звонка дополнительно `pnpm livekit:up` и `pnpm agent:dev`.

```powershell
pnpm db:up ; pnpm db:migrate ; pnpm db:seed
```

```powershell
pnpm portal:hash   # спросит пароль, напечатает bcrypt-хеш для .env
pnpm portal:dev    # http://localhost:3000
```

Портал подключается к базе ролью `portal_app`, а не владельцем схемы:

| Переменная | Что это |
|---|---|
| `PORTAL_DATABASE_URL` | строка подключения под `portal_app`; пароль — `PORTAL_APP_PASSWORD`, его выставляет `pnpm db:migrate` |
| `PORTAL_RESTAURANT_SLUG` | `restaurants.slug` ресторана, которым управляет этот экземпляр (в `db/seed.sql` — `demo`) |

Если `PORTAL_APP_PASSWORD` пуст, `pnpm db:migrate` предупреждает и оставляет роль
`NOLOGIN` — портал тогда не сможет прочитать ни одной страницы со справочником.

Если портал падает с `28P01`, пароль роли в базе разошёлся с `PORTAL_DATABASE_URL`.
Синхронизирует их одна команда, схему она не трогает:

```powershell
pnpm db:passwords
```

Тесты этот пароль больше не портят: роли в PostgreSQL общие на весь кластер, поэтому
`db/tests/global-setup.ts` мигрирует тестовую базу с `syncRolePasswords: false`, а проверка
прав переключается на роль через `SET LOCAL ROLE` вместо входа по паролю.

Открывать строго `http://localhost:3000`: микрофон браузер отдаёт только в защищённом
контексте, по адресу вида `http://192.168.…` его не будет.

Корневой `.env` подгружает `next.config.ts` — Next сам читает `.env` только из папки
приложения, а репозиторий держит один файл на всё (как и агент).

## Роли

Учётки — в переменных окружения (§7.1): `ADMIN_USERNAME` / `ADMIN_PASSWORD_HASH`,
`OPERATOR_USERNAME` / `OPERATOR_PASSWORD_HASH`, секрет подписи `SESSION_SECRET`.
Пароль хранится только bcrypt-хешем стоимости 12; конфигурация отвергает значение,
не похожее на хеш.

Тестовый звонок доступен обеим ролям одинаково (§7.2). Роль лежит в подписанной cookie
`portal_session` (JWT HS256, 8 часов, `HttpOnly; SameSite=Strict`) и видна в шапке.
Проверок две и они независимы: `proxy.ts` закрывает маршруты целиком, а каждый серверный
обработчик дополнительно зовёт `guardRequest` — скрытая кнопка защитой не является.

Вход ограничен: 5 попыток на IP за 15 минут, дальше 429. Счётчик живёт в памяти процесса —
при нескольких репликах портала понадобится общее хранилище.

## Приватность

- Транскрипт живёт только в состоянии React: ни на сервер, ни в `localStorage` он не уходит
  и исчезает при перезагрузке страницы (§7.3, §11.3).
- Портал не пишет в лог ни транскрипт, ни логин, ни причину отказа во входе.
- Аудио через портал не проходит вообще: голос идёт напрямую в LiveKit.

## Структура

| Путь | Что там |
|---|---|
| `proxy.ts` | первый рубеж: без сессии страницы уходят на `/login`, API — в 401 |
| `lib/config.ts` | env через zod; при некорректном конфиге портал падает |
| `lib/session.ts` | подпись и проверка cookie (jose) |
| `lib/users.ts` | учётки из env и bcrypt-сверка (только Node-рантайм) |
| `lib/rbac.ts` | `guardRequest` для API, `requireSessionForPage` для страниц |
| `lib/rate-limit.ts` | лимит попыток входа |
| `lib/livekit.ts` | выпуск токена на разовую комнату |
| `lib/db.ts` | один пул `postgres.js` на процесс, роль `portal_app` |
| `lib/restaurant.ts` | id ресторана по `PORTAL_RESTAURANT_SLUG` |
| `lib/tables.ts`, `lib/menu.ts` | запросы справочников; `sql` и `restaurantId` — параметры |
| `lib/schemas/` | zod-схемы форм, повторяющие `CHECK` из миграций 002 и 003 |
| `lib/db-errors.ts` | SQLSTATE → `duplicate` / `in_use` / `invalid` |
| `lib/api.ts` | общая обвязка маршрутов записи: роль, разбор тела, коды ответов |
| `components/test-call.tsx` | подключение, микрофон, звук агента, живой транскрипт |
| `components/tables-manager.tsx`, `components/menu-*.tsx` | экраны справочников |
| `components/ui/` | боковая панель формы (Esc, ловушка фокуса) и тумблер |
| `scripts/hash-password.ts` | печать bcrypt-хеша, пароль вводится скрыто |

## Тесты

```powershell
pnpm test --project portal
```

Сети, ключей и LLM в тестах нет (AGENTS.md §4): проверяются конфигурация, сверка пароля,
подпись и срок сессии, лимит попыток, схемы форм, перевод ошибок базы и все маршруты API —
включая права внутри выпущенного токена LiveKit и отказ оператору на запись.

Запросы к базе проверяются отдельно, против настоящего PostgreSQL в Docker:

```powershell
pnpm test --project database
```

Файлы `portal/tests/db/*.test.ts` входят в проект `database`, а не `portal`: базу
пересоздаёт один `db/tests/global-setup.ts`, и второй проект со своим setup сносил бы её
из-под первого. Живой звонок проверяется руками по
`docs/manual-tests.md`.
