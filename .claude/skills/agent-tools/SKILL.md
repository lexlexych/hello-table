# Инструменты агента

Список инструментов и их транспорта — docs/PROJECT.md §6. Агент вызывает разрешённые
Postgres-функции напрямую под ролью `agent_app`; доступа к таблицам у него нет. n8n остаётся
для workflow, запускаемых из чата или формуляра, и не является промежуточным слоем звонка.

## Порядок — строго такой, не перескакивать

1. **Контракт** в `docs/tool-contracts.md`: назначение, вход, выход, ошибки. Ответ
   функции — строго типизированная структура, никакого свободного текста: агент
   передаёт результат в LLM, и непредсказуемый формат заставит модель выдумывать.
2. **Zod-схема** в `packages/contracts/src/tools.ts` — единственный источник типов.
   Дублировать типы в агенте или портале запрещено.
3. **Postgres RPC** (по навыку db-migrations): корректность и атомарность остаются в
   `SECURITY DEFINER`-функции; роль `agent_app` получает `EXECUTE` только на нужную функцию.
4. **Регистрация в агенте** (`agent/src/tools/`): TypeScript-обёртка делает параметризованный
   вызов RPC, переводит SQLSTATE в перечислимый код и валидирует результат zod-схемой.

## Обязательные требования к каждому инструменту

- **Филлер-фраза перед вызовом** на языке разговора («Einen Moment, ich schaue nach» /
  «Секунду, проверяю» / «One moment, let me check»). Реализуется хуком перед вызовом
  инструмента, а не промптом — LLM забудет это делать. Фразы — из `agent/src/i18n/`.
- **Таймаут и обработка ошибок базы.** При недоступной базе или ошибке агент произносит
  внятное извинение на языке разговора и предлагает обратный звонок; молчаливое
  зависание запрещено.
- **Валидация ответа** zod-схемой на стороне агента до передачи результата в LLM.
- **Тест (vitest)** на каждый инструмент: happy path + доменная ошибка + недоступная база +
  невалидный ответ. Postgres-клиент инструмента подменяется фейком; реальные внешние API,
  ключи и LLM запрещены. Интеграционные тесты самой RPC живут в `db/tests/`.
