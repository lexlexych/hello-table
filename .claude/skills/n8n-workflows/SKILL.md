# Workflow n8n

n8n — оркестрация и интеграции (клей), не источник истины. Разделение ответственности —
docs/PROJECT.md §3.4, безопасность вызовов — §3.5.

## Структура каждого workflow-инструмента

1. **Первый узел — проверка HMAC**: заголовок `X-Signature` = HMAC-SHA256 тела запроса
   с секретом `N8N_WEBHOOK_SECRET`. Невалидная подпись → отказ, дальше выполнение не идёт.
2. **Второй узел — валидация входа**: обязательные поля, типы, существующий и активный
   `restaurant_id`.
3. **Вызов Postgres-функции** из PROJECT.md §5.2 — под ролью `n8n_app` (у неё только
   EXECUTE на функции, прав на таблицы нет).
4. **Строго типизированный ответ** по контракту из `docs/tool-contracts.md` и zod-схеме
   из `packages/contracts`. Никакого свободного текста и «лишних» полей.

## Запреты

- **Никакой бизнес-логики в Function-узлах.** Поиск слотов, расчёт сумм, проверки
  вместимости, блокировки — только в Postgres-функциях. Function-узлы n8n не дают
  транзакционных гарантий.
- **В Telegram не передавать имя и телефон клиента** — только категория, язык, время и
  ссылка `https://app.<домен>/callbacks/<id>` (PROJECT.md §11, вариант «а»).

## После изменения

Экспортировать workflow в JSON в `n8n/workflows/` и закоммитить. Workflow, не
экспортированный в репозиторий, считается несуществующим.
