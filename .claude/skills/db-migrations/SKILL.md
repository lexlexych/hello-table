# Миграции и схема базы данных

Модель данных и функции определены в docs/PROJECT.md §5. Разделение ответственности
n8n / Postgres — §3.4: всё, что требует корректности и атомарности, живёт только здесь.

## Правила

1. **Нумерация.** Миграции — нумерованные SQL-файлы в `db/migrations/`:
   `NNN_short_name.sql` (001, 002, …). Порядок применения — строго по номеру.
   Применённые миграции не редактируются — только новая миграция поверх.
2. **Обратимость.** Каждая миграция имеет понятный путь отката (секция `-- down` или
   парный файл). Если откат невозможен (удаление данных) — это явно написано в шапке файла.
3. **Функции отдельно от таблиц.** Тела функций живут в `db/functions/` — по файлу на
   функцию, `CREATE OR REPLACE`. Миграции меняют таблицы; функции переприменяются скриптом.
4. **Тест на гонку обязателен** для любой функции, создающей бронь или заказ
   (`create_reservation_atomic`, `create_pickup_order_atomic`): параллельные вызовы в
   тесте не должны дать двойное бронирование столика или перепродажу слота самовывоза
   (`SELECT ... FOR UPDATE`). Без такого теста функция не считается готовой.
5. **`delete_after` обязателен** во всех таблицах с персональными данными; заполняется
   триггером: брони — визит + 30 дней, заказы — выдача + 30 дней, обратные звонки —
   обработка + 14 дней. Ночное задание вызывает `purge_expired_personal_data()`.
6. **Роли** — по PROJECT.md §5.3: `app_owner` (только миграции), `n8n_app` (только
   EXECUTE на функции из §5.2, никаких прав на таблицы), `portal_app`. Функции —
   `SECURITY DEFINER`, владелец `app_owner`.
7. **Никакой тяжёлой ORM.** Портал ходит через `postgres.js`; агент к базе не ходит
   вообще — только к вебхукам n8n.
8. **Тесты** — vitest против локального Postgres в Docker. Реальные внешние API и
   LLM в тестах запрещены.

## Порядок работы

Сверка с PROJECT.md §5 → миграция → функции → тесты (включая гонку) → seed при
необходимости → проверка отката. Изменение схемы после деплоя — только с проверкой
бэкапа (навык deployment).
